Documentation/Reference/Flight and Locomotion

LCM Nav3D: Realistic Flight/Swim Locomotion Reference

Applies to LCM Nav3D 3.6.0 · Unreal Engine 5.2 to 5.8 · Updated 22 November 2026

Realistic 6-DOF movement for flying and swimming pawns (drones, birds and fish), on top of LCM Nav3D navigation. The navigation gives the guidance (where to go), and this layer gives the dynamics (how the body moves there, following basic physics).

Concept: Guidance → Control → Dynamics

  • Navigation (as before): the SVO path or flow field, then pure-pursuit steering and CBS/ORCA avoidance, give a desired velocity.
  • ULcmFlightMovementComponent: takes that desired velocity and runs a 6-DOF rigid-body flight or swim model for the body's archetype (thrust, lift and drag, gravity or buoyancy, attitude control). It moves the pawn and fills in a struct for animation.

Quick start

  1. Add a Lcm Flight Movement Component to a pawn whose root is a collision shape.
  2. Set: bEnabled = true, LocomotionModel = FlightDynamics, Archetype (Multirotor / Bird / Fish / Generic6DOF), and tune FlightConfig.
  3. Drive it one of two ways:
    • From navigation (recommended): on the pawn's BT or StateTree FlyTo task, tick Use Flight Movement Component. The task then sends the guidance to the component.
    • By hand: call RequestVelocity(WorldDesiredVelocity) every tick from your own code or Blueprint.

It is off by default. With bEnabled=false (or the task option off), the pawn moves with the older kinematic FlyTo, as before.

Already have a movement component on the pawn? You can leave it there. While the flight component is enabled, it is the only thing that moves the pawn. Any other movement component on the same root (FloatingPawnMovement, CharacterMovement, ULcmNavMovementComponent) is paused: its velocity is set to zero, it is deactivated and it stops ticking. It is put back exactly as it was as soon as the flight component stops (bEnabled=false, the component is deactivated, or the pawn is destroyed). Without this, Unreal would run both on one body. The last one to tick would overwrite the pawn's velocity, and a CharacterMovement would keep pulling the body down with gravity. You can turn this off for one component with Pause Conflicting Movement Components, or for the whole project with r.LcmNav.Flight.MovementAuthority 0.

Two more things. Stock MoveTo path following still uses the pawn's original movement component, so drive the flight component with FlyTo (or RequestVelocity). And the pawn's root must not have Simulate Physics turned on; the component writes a warning to the log if it does.

Stopping at the goal (Hold Station When Idle)

A movement component is told what velocity to have, so "stop" used to mean "aim for zero velocity". A body with momentum then coasts until drag slows it down, and nothing brings it back. In our tests, bodies that arrived inside a 150 cm sphere and were told to stop ended up well past the goal: a multirotor 267 cm, a jet 936 cm, a fish 2369 cm, and the bird 14,790 cm away and still descending.

Hold Station When Idle (on by default, r.LcmNav.Flight.HoldStation) fixes this. When guidance stops, the component steers the body gently back to the point where guidance stopped, and lets it come fully to rest. Any RequestVelocity call takes over straight away, so it only affects a body that has nothing else to do. With it on, all four archetypes settle within about 2 m of the goal and stay there.

Debugging the flight path: planned vs predicted vs flown

Turn on bDrawPathfindingDebug on the navigation manager (it switches on all path debugging), and a pawn with a flight component draws three lines:

line what it shows switch
Orange polyline + red spheres the PLANNED path from the planner manager bDrawPathfindingDebug
Magenta arc ahead of the pawn the PREDICTED flight path: the component's dynamics run ahead along the rest of the route, including look-ahead, banking and braking component bDrawDebugPrediction (default on) / r.LcmNav.Flight.DebugPredict, horizon r.LcmNav.Flight.DebugPredictSec
Green→red fading trail behind the FLOWN trajectory (speed-coloured), plus yellow = velocity and cyan = guidance arrows component bDrawDebugTrail (default off) / r.LcmNav.Flight.DebugTrail, lifetime r.LcmNav.Flight.DebugTrailSec

How to read them: the gap between orange and magenta comes from the body's physics (cutting corners, braking distance), which is normal. The gap between magenta and the trail comes from avoidance while flying (other agents, walls), which the prediction leaves out because it can't know what other agents will do. If a single agent on its own leaves the magenta line, that is a bug, so please report it. None of the three are drawn in Shipping builds.

Winged bodies (Jet, Bird): how they fly, and how to tune them

Both use the same wing model, and it flies like an aircraft, not like a hovering drone:

  • It turns by banking. The heading error sets a bank angle, the tilted lift pulls the body round, and the nose follows the velocity. So a winged body has a real minimum turn radius, v² / (g·tan(MaxBankAngleDeg)): 212 cm at 600 cm/s and 60°. Raise MaxBankAngleDeg (and MaxLiftFactor with it) for tighter turns, or lower it for a heavy bomber.
  • Lift holds the body up, and thrust only has to beat drag. At cruise the throttle sits near drag/MaxThrust (about 0.12 with the defaults). LiftCoeff sets how much airspeed the wing needs: the weight is held up when LiftCoeff·v² = Mass·980.
  • A wing alone can't stop on a point. Told to stop hard, a wing has nothing to push against. The Jet switches to vectored thrust below WingBorneSpeed, and the Bird flares to lose speed and then flaps to hover. Both need the navigation to slow them down as they arrive. If they are told to fly at full speed all the way, a fast body will circle its goal.
  • Arriving and staying are different. When a FlyTo task arrives, it stops sending guidance. The flight component then holds the position where it was left instead of coasting on (see Hold Station When Idle above). Without that, a winged body would fly past its goal and not come back.
  • The Jet is a reworked Generic6DOF. The enum name stayed the same, so existing content keeps working. r.LcmNav.Flight.JetGeneric 0 brings back the old hover-thruster behaviour.

Notes:

  • A fast bird or fish can't stop on a point. The navigation's arrival slowdown makes it flare in to a perch. Without that slowdown, a fast body circles its goal.

  • Realistic bodies react to guidance with a delay. Raise MaxAcceleration for a quicker body, or lower it for a heavier one that drifts more.

  • The two control loops work together, so tune them as a pair. VelocityP is the outer loop (time constant 1/VelocityP). It asks for a tilt, and the inner AttitudeP/AttitudeD loop then has to reach that tilt. Keep the inner loop about 4× faster than the outer one. Otherwise the body wanders from side to side and swings back and forth around its goal:

    formula shipped default
    inner natural frequency wn = sqrt(AttitudeP) 7.75 rad/s
    inner damping ratio z = (AttitudeD + AngularDrag) / (2*wn) 0.84
    inner time constant 1/(z*wn) 0.15 s
    outer time constant 1/VelocityP 0.67 s

    Note: AngularDrag adds to AttitudeD. The simulation applies -AttitudeD*w and then -AngularDrag*w, so the real damping is the sum of the two. If you raise AttitudeP for a quicker body without raising AttitudeD too, z drops below about 0.7, and the body visibly wobbles after every change of heading. Damping has to grow as 2*z*sqrt(AttitudeP).

Altitude while manoeuvring: MaxTiltAngleDeg and the thrust budget

A body that tilts to move sideways (Generic6DOF or Multirotor) only uses cos(tilt) of its thrust against gravity. To hold its height while tilted, it needs a thrust-to-weight ratio of 1/cos(tilt):

tilt lateral accel available thrust-to-weight needed just to hold height
30° 566 cm/s² 1.15×
45° 980 cm/s² 1.41×
60° (default) 1697 cm/s² 2.0×
75° 3657 cm/s² 3.9×

MaxTiltAngleDeg limits the tilt, so the body doesn't tilt so far that it loses height. When there isn't enough thrust for everything, height is kept first, and sideways movement gets what is left. Note: if you raise the tilt limit without raising MaxThrust to match, the body sinks during hard sideways moves, and the harder it moves, the faster it sinks. Keep MaxThrust ≳ Mass * 980 / cos(MaxTiltAngleDeg). With the defaults (1 kg, 3000, 60°) there is 2× to spare.

Reaching the commanded speed: drag is fed forward

The velocity loop adds back the drag it is about to apply, the same way it adds back gravity. Without this, drag would keep the body below its target speed by |drag| / (Mass * VelocityP). With the default settings that is 336 cm/s out of 600 cm/s, so the body would cruise at 44 % of the speed it was given. Changing gains doesn't fix that: raising VelocityP makes the gap smaller, but the body then leans less. To turn it off: r.LcmNav.Flight.DragFeedForward 0.

Making a body lean (tilt-to-translate look)

A body that steers with its thrust leans because the thrust has to point along Mass*accel + weight. In FlightDynamics mode there is no setting just for the look of the lean. The tilt comes from the physics, so you change the lean by changing what the body has to do. There are three different causes, and they are easy to mix up:

Want Knob Why
Forward lean while cruising LinearDragCoeff.X/Y ⬆ At a steady speed there is no acceleration, so the lean is atan(drag/weight). Control gains don't change it. Going from 0.5 to 1.4 changes it from 10° to 28° at 600 cm/s.
Lean while accelerating/braking VelocityP ⬇ The largest lean is atan(VelocityP*MaxSpeed/g), but it fades over 1/VelocityP. A high gain gives a lean too short to see; a low gain gives a smaller lean that lasts.
Bank into turns YawP ⬇ (keep ≪ AttitudeP) The body only banks while it needs to move sideways. A fast yaw turns the nose to the new heading first, so the body then just moves forward: it pivots and goes, without banking.

Note: none of this applies in Kinematic mode. There the tilt is only for looks, set by BankingAmount and MaxBankingAngle.

BankingAmount is now a multiple of the physically correct bank

BankingAmount (in Kinematic mode, and the same field on the BT and StateTree FlyTo) multiplies the real bank angle for the turn, tan(bank) = V * yawRate / g. 1 is the bank a real body would use in that turn. Above 1 exaggerates it so it is easier to see, and 0 keeps the wings level.

Note: the default changed from 4 to 1, and an old value doesn't mean the same thing any more. The previous formula used a normalised per-frame velocity change, which loses how hard the turn is. As a result the roll command stayed near ±1 from ordinary velocity noise, and the body flicked between ±4° every frame in straight flight. With the new formula, a value of 4 reaches MaxBankingAngle in any normal turn. If you had set your own value here, tune it again starting around 1. To use the old formula: r.LcmNav.Flight.CoordinatedBank 0.

Flying straight up or down

The body's orientation is now worked out from its orientation in the previous frame (parallel transport), not from the world's up direction. The two usual Unreal functions for building a rotation jump when a body moves straight up or down, and both were used before:

  • FVector::Rotation yaws by atan2(Y, X), which at X = Y = 0 is atan2(0,0) = 0: a body climbing straight up snaps its heading to world +X, then swings with any lateral noise.
  • FRotationMatrix::MakeFromXZ switches its up direction to (1,0,0) once |Fwd.Z| passes 1 - KINDA_SMALL_NUMBER, so the rotation jumps instead of changing smoothly.

Either one makes an agent roll hard when it climbs or dives, with nothing in its flight path to explain it. Levelling to the world's up direction is still used, but less the more vertical the movement is, so a body flying straight up just keeps its roll. This applies to Kinematic, Bird, Fish and both FlyTo tasks. To turn it off: r.LcmNav.Flight.ContinuousFrame 0.

The vertical axis has its own gain: VelocityPZ

VelocityP is kept low on purpose. Sideways, it asks for a tilt that the attitude loop has to reach, so it must stay about 4× slower than that loop. Up and down there is no such limit, because thrust acts directly without any tilt. So sharing the slow gain only made height control slower. Real multirotor flight controllers keep these separate too (PX4 MPC_Z_VEL_P and MPC_XY_VEL_P; ArduPilot PSC_VELZ_P and PSC_VELXY_P).

Tested on a rig flying a dead-level path, so any height change comes from the controller:

VelocityPZ settled altitude wander settled vertical speed
legacy (shares VelocityP = 1.5) 40.3 cm 33.4 cm/s
2 26.1 30.3
4 (default) 6.0 cm 12.1 cm/s
8 5.4 9.9

Sideways error and arrival time stayed the same in testing (173.8→173.6 cm, 10.85→10.83 s), so there is no cost sideways. The value 4 comes from the maths. The position loop's damping, ζ = 0.5·√(Kz·L/v), reaches 1.0 at Kz=4 when the look-ahead equals the speed. The velocity loop's damping against rotor spin-up, ζ = 1/(2√(Kz·τ_spool)), is 0.707 at Kz=4 with RotorSpinUpRate 8. If you set it much higher than 4, raise RotorSpinUpRate as well.

A path that ends short of the goal no longer orbits

If the last waypoint of the path is more than 2 × Acceptance Radius from the goal, the task used to reset its index to that waypoint every tick. The agent was already within the acceptance radius of it, so on the next tick the waypoint was marked as reached and the index was reset again. In one test this happened 1750 times in 40 s, and the task never succeeded or failed. Now it does this once, holds position, replans twice, and then reports Failed with a log line that names the likely cause. A path usually ends short because the goal was moved to the centre of a leaf, or because r.LcmNav.SeamSafe.TruncateUnprovable (on by default) cut the route at the first part it couldn't confirm.

Each row below is a known cause with its own console variable, so you can turn each fix on or off separately. Go down the list in order. Don't start by re-tuning gains, because none of these problems comes from the gains.

Note: r.LcmNav.WallAvoidV2 is off (0) by default on purpose. An earlier attempt to weaken this push made one agent fail to arrive (it orbited, with 33 loop events), because a planned route sometimes points into a wall and only a full-strength push gets the agent clear. V2 keeps the full push at contact and only reduces it further away, but it hasn't been re-tested in that case yet. Turn it on if flyers judder near geometry, and check that they still arrive.

Agent scale: flying a body in a centimetre world

ULcmFlightMovementComponent::AgentScale (default 0) lets a body that was set up for a metre-scale world fly in a centimetre-scale one, with no retuning. The simulation runs in agent units, so every FlightConfig value and every built-in value (gravity, airspeed limits, how close counts as holding station) keeps its usual meaning. Positions and velocities are converted on the way in and out: world = agent × scale. 0 takes the scale from the FlyTo task that drives the body (its own Agent Scale, or the navigation manager's World Scale); any positive value is used as it is.

At 0.01, a 1 m drone tuned for 600 cm/s flies as a 1 cm drone at 6 cm/s, along the same path shape, in the same time. This has two results. FLcmFlightState is reported in agent units (Speed01 doesn't change, and Airspeed and VerticalSpeed read 600 at full speed at any scale). And you have to scale the pawn's own collision and mesh yourself, because the plugin only scales the movement. In a 120 × 70 × 40 cm aquarium at a 1 cm leaf, a drone at actor scale 0.01 flies the same cave route it flies at 100:1.

Animation contract: FLcmFlightState

Every tick, the component fills in FLcmFlightState. Most fields mean the same thing for every archetype:

Field Meaning
Speed01 Normalized airspeed (|velocity| / MaxSpeed): blendspace axis
VerticalSpeed cm/s, climb + / dive −: climb/dive pose blend
BankAngleDeg / PitchDeg Body roll / pitch: additive lean/pitch
YawRateDeg Turn rate: lean/tilt into turns
GaitPhase A value that cycles from 0 to 1: rotor spin, wingbeat or tail beat
GaitAmplitude01 Throttle (drone) / flap-glide blend (bird) / undulation vigour (fish)
RotorRPM Multirotor rotor RPM
Throttle01 / Airspeed Commanded effort / raw speed

You can read it in two ways:

  • Ask for it: call GetFlightState (BlueprintPure) on the component, for example from an Animation Blueprint's Update.
  • Have it sent to you: implement ILcmFlightAnimInterface::ReceiveFlightState on your Animation Blueprint (or pawn). The component calls it every tick (bBroadcastAnimState, on by default). Store the struct and use it like this:
    • GaitPhase → rotor/wing/tail cyclic pose (Sine/curve on the phase)
    • Speed01 + VerticalSpeed → locomotion blendspace
    • BankAngleDeg / PitchDeg → additive lean/pitch
    • GaitAmplitude01 → flap-vs-glide (bird) or effort (fish/drone) blend weight
    • RotorRPM → prop-spin material/WPO param (Multirotor)

Mass crowds & scale

The LCM Nav3D Agent trait (NavMode = PathFollowing) has the same flight options (LocomotionModel, FlightArchetype, FlightConfig). Set them, and a whole crowd flies with the same 6-DOF physics as a pawn, while still following paths, avoiding each other and arriving. With the default Kinematic, crowds behave as before.

Dynamics LOD (for large crowds). Full 6-DOF for every agent is expensive. Set FlightDynamicsLODDistance (cm), and only agents within that distance of the camera run full dynamics. The others use the cheap kinematic movement (they face their velocity and don't roll). So in a crowd of 10,000, only the agents near the camera cost the full price. 0 = full dynamics for everyone. To turn it off for the whole project: r.LcmNav.Mass.FlightLOD 0 (1 is the default). Switching between the two is smooth: when a far agent comes back into range, its simulation starts again from where it is.

Not included yet:

  • GPU 6-DOF compute for very large crowds is not included. The dynamics LOD on the CPU already limits the cost to the agents you can see, which is cheaper.
  • Shared flight config: FlightConfig is currently stored per entity. Sharing one copy per archetype would use less memory in large crowds, but that isn't done yet.

Determinism

The dynamics are deterministic. They use fixed simulation steps, and no random numbers or real-time clock. Gusts and jitter come from smooth noise that is the same for an agent every time. So the same input always gives the same flight.

Bird and Fish do not share the drone control cascade

Note: birds and fish use their own simulation (StepBird and StepFish), not the drone one (RunStep6DOF). That is on purpose, because a bird doesn't move sideways by tilting a rotor. But it meant they also didn't have the drone's speed-tracking loop. Their thrust only pushes forward, so in older versions nothing corrected a sideways speed error. The bodies pointed in the guidance direction and waited for drag, so errors across the path and in height only faded slowly and never reached zero. That was why birds and fish "drifted away from the path points".

They now make the sideways force a banked wing or a bending body really makes, up to what the body could produce: lift for the bird, and tail and fin thrust, scaled by swim effort, for the fish. BankTurnGain is the rate (1/s) that turns a speed error in cm/s into that force, as its description always said. Tested on one corner path with the same guidance:

archetype cross-track before → after altitude error before → after
Generic6DOF (reference) 174.3 → 174.3 9.4 → 9.4
Multirotor (reference) 173.6 → 173.6 22.8 → 22.8
Bird 234.4 → 183.9 69.7 → 61.5
Fish 203.7 → 198.4 64.0 → 17.4

The two drone archetypes are not affected, because the change only touches the two integrators that didn't have the loop. Kill switch r.LcmNav.Flight.BodyManeuver 0.

Note: the bird's LiftControl trim is not a second vertical controller, so don't remove it. It is the only way the bird balances lift against gravity. Lift is LiftCoeff × airspeed², which at cruise is more than the body's weight, so without the trim the bird keeps climbing (in testing, altitude error went from 61.5 to 186.4 cm). The trim sets how strong the lift is, and the manoeuvre force pushes sideways. Both are needed.

Fish: the tail beats with the swim

A real fish's tail beats faster the faster it swims, with a swing of about a fifth of its body length, and hardly moves at rest while the fins hold it in place. Tail Beat From Speed (Flight Config, Flight|Fish, on by default) animates the fish material the same way. When it is off, the older fixed beat plays.

Field Default Meaning
Tail Beat From Speed on The beat follows the speed in body lengths a second
Tail Beat Hz Per Body Length 1.33 Beats a second per (1 + body lengths a second): about 2.7 at 1 body length a second. Lower for a stiff swimmer (a tuna), higher for an eel-like one
Tail Beat At Rest Hz 0.7 The beat at rest
Tail Amplitude BL 0.2 The tail tip's swing while swimming, peak to peak, in body lengths. 0 = the material's authored swing
Tail Amplitude At Rest BL 0.05 The swing at rest

A fish with a skeletal mesh that plays one looping swim animation gets the same rate. Drive Swim Clip Rate on the Flight Movement component (LCM Flight|Anim, on by default) sets the animation's play rate from the beat. Swim Clip Beats Per Loop is how many tail beats one loop contains; 0 counts them from the animation's bones the first time it plays. An Animation Blueprint can read the same rate from the flight state (Gait Frequency Hz).

Schooling fish also stay out of each other's wake. Wake Avoid Weight (0.8) moves a fish to the side when another fish is directly ahead within Wake Length BL (2 body lengths). So a school swims side by side and at an angle behind each other, instead of nose to tail.

Fish schooling on pawns

The Flight Movement component has a Schooling group (LCM Flight|Schooling). Turn on Enabled, and the fish steers as part of a school, whichever node drives it (Fly To, Patrol, Follow, Orbit or Follow Flow Field). The school steering replaces the node's own avoidance (push, wall checks, flock separation). It keeps personal space, sees collisions coming, matches heading and stays close to other fish (pawns and Mass fish alike), and turns away from rocks and glass before reaching them. The node's route still decides where to go, and the fish's nose follows the direction it swims (a Patrol's facing request isn't used). Nodes that need exact control (Land, Take Off, Move To And Face, Use Smart Object and the evade nodes) keep their own steering.

On Patrol, a schooling fish counts a waypoint as reached once the school has carried it past (beyond the waypoint along the leg leading to it, and within 3 × the Arrival Radius). So a fish on the edge of the school doesn't turn back for a point it passed to the side of.

The settings are the same as for a Mass crowd. The table, and the leadership, predator, speed and burst-and-coast options, are in the Mass Traits Reference. Three things are different for pawns:

  • Informed Fraction doesn't apply, because every pawn follows its own route.
  • Contact Push (default 0.5) pushes apart overlapping bodies, scaled by overlap depth.
  • A predator is any body at least one and a half times the fish's size that isn't schooling with it. So a larger pawn with its own flight model (like the Fish Tank's predator) makes the school escape.

A school on a loop (Feature Examples 2.7). We tested thirty fish on one Patrol loop. Give the loop many waypoints (one or two body lengths apart along the curve, with turns at least a metre in radius) and an Arrival Radius of about two waypoint gaps. Each fish then swims to a point just ahead on the curve, and its neighbours aim at nearly the same point. With only twelve waypoints, fish at the same turn chased points 90-180 degrees apart, and the school broke up at every end. Speed Coupling 0.4 keeps the school's shape on the straights, and Threat Time Seconds 1.5 with Threat Range BL 2.5-3 lets it part round a predator without touching it.

With Enabled off, a Fish-archetype body still keeps its personal space: it keeps its distance, sees collisions coming and pushes apart on contact. It doesn't match heading, close up, avoid walls, follow leaders or escape. r.LcmNav.FishSchool.PersonalSpace 0 turns this off. Every flight body counts as a neighbour of the others, whether or not its pawn has a Navigation Invoker.

More rules for the Fish archetype, each with a console variable to turn it off:

  • Turn-aware arrival (r.LcmNav.Flight.TurnAwareArrival): the fish slows down until its turning circle (speed / Max Turn Rate) is small enough to reach the point it is swimming to. So it doesn't circle a goal it approaches from the side.
  • Stay in the water (r.LcmNav.Flight.FishStayInWater): a fish inside a Water Volume doesn't leave it. A move that would take it out stops just under the surface, and the part of its velocity pointing out is removed. If another Water Volume continues from that face, it is all water, and the fish swims on.
  • The water is a boundary (r.LcmNav.WaterSurfaceIsBoundary, r.LcmNav.WaterVolumeIsClosed): every face of a Water Volume (its surface, its sides and its floor) is blocked in the octree. So a swimmer's routes stay in the water and a flyer's stay out of it, with or without glass. A face, or the part of a face, where another Water Volume continues stays open. (Before 3.5 only the surface was blocked. A route to a goal above the water could leave an open tank through its side, and the fish was then stuck against that invisible wall.) Volumes wider than r.LcmNav.WaterSurfaceMaxSizeCm (200 m, such as a sea) get no boundary.
  • A target out of the water (r.LcmNav.Flight.FishGoalInWater): when a fish in a Water Volume chases a target actor (a Fly To's goal object, or the Fly To Location node's Target Actor), or patrols to a waypoint outside its water, it swims to the nearest point in its water instead, one and a quarter radii in from the faces. For bait above the surface it swims up under it, and for a target behind the glass it swims to the nearest glass. A fixed Fly To destination outside the water still fails with No Path, so that you find out about the mistake. When the fish can see its goal (same water, nothing solid in between), it swims straight at it. That way it can reach the surface and the glass, which the octree's padding (sized for the largest flyer in the level) keeps routes away from. Its route requests always start and end in open water inside its own volume.

To tune schools without editing assets, use these console multipliers: r.LcmNav.FishSchool.ScaleRepulsion, ScaleAnticipation, ScaleAlign, ScaleAttract, ScaleWall, ScaleEscape, ScaleContactPush and ScaleBrake (1 = the asset's value). Also r.LcmNav.FishSchool.MaxCommandDeg (-1 = the config's value) and r.LcmNav.FishSchool.Leadership (0 = every fish steers for the goal).

Path following on 6-DOF bodies

Everything in this section applies only to a pawn driven by an enabled ULcmFlightMovementComponent in FlightDynamics (6-DOF) mode. The defaults are LocomotionModel = Kinematic and bUseFlightMovementComponent = false, so a pawn with default settings doesn't use any of it. Kinematic pawns, and pawns with no flight component, follow paths the same way they always have.

On a 6-DOF body the path follower works differently in four ways:

  • Sharp corners. The agent's position on the path is found by projecting it onto the path, not only by checking whether it came within Acceptance Radius of each waypoint. So a small Acceptance Radius no longer makes agents stick at corners that are tighter than their turning circle. r.LcmNav.PathProjectWindow (default 3) limits how far ahead the search looks, so on a hairpin the agent doesn't jump to the return leg before it has rounded the corner.
  • Stall detection. A stall means no progress along the path, not no movement. This way an agent that flies in circles is noticed and recovered. Turn it off with r.LcmNav.ProgressStallDetect 0. The progress threshold is r.LcmNav.ProgressEpsilonCm (default 50).
  • The look-ahead target. The point the agent steers at is pulled back along the path until there is a clear line to it in the octree. In a vertical shaft with offset openings, for example, this stops the agent aiming through a floor. Where there is no navigation data yet, the target is left unchanged. Turn it off with r.LcmNav.PursuitVisibleTarget 0.
  • Speed for corners. The agent plans its speed over the next few waypoints (r.LcmNav.SpeedProfilePoints, default 8) and starts braking early enough for every corner it can see. In testing, corner error stayed about the same from 300 to 1200 cm/s, and average speed hardly changed.

Acceptance Radius does not control how closely the agent follows the path. It only decides when a waypoint counts as reached. How tightly an agent can take a corner depends on its physics: the minimum turn radius is v²/a_eff, so waypoints closer together than that are always taken wide, however you tune it.
