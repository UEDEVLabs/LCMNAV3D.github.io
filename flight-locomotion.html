Documentation/Reference/Flight and Locomotion

LCM Nav3D - Realistic Flight/Swim Locomotion Reference

Applies to LCM Nav3D 3.6.0 · Unreal Engine 5.2 to 5.8 · Updated 22 November 2026

Ultra-realistic 6-DOF locomotion for flying/swimming pawns (drones, birds, fish), layered on top of LCMNav3D navigation. The nav system provides guidance (where to go); this layer provides physically-plausible dynamics (how the body moves).

Concept - Guidance → Control → Dynamics

  • Nav (unchanged): SVO path / flow field → pure-pursuit + CBS/ORCA avoidance → a desired velocity.
  • ULcmFlightMovementComponent (new): consumes that desired velocity and runs a 6-DOF rigid-body flight/hydro model (thrust, lift/drag, gravity/buoyancy, attitude PID) per archetype, producing the pawn transform and an animation-drive struct.

Quick start

  1. Add a Lcm Flight Movement Component to a pawn whose root is a collision primitive.
  2. Set: bEnabled = true, LocomotionModel = FlightDynamics, Archetype (Multirotor / Bird / Fish / Generic6DOF), and tune FlightConfig.
  3. Drive it one of two ways:
    • Nav-driven (recommended): on the pawn's BT/StateTree FlyTo task, tick Use Flight Movement Component. The task feeds guidance automatically.
    • Manual: call RequestVelocity(WorldDesiredVelocity) each tick from your own code/Blueprint.

Off by default: with bEnabled=false (or the task flag off) nothing changes - motion is the legacy kinematic FlyTo.

Already have a movement component on the pawn? Leave it there - nothing to remove. While the flight component is enabled it takes sole movement authority: any other movement component driving the same root (FloatingPawnMovement, CharacterMovement, ULcmNavMovementComponent) is automatically paused (velocity zeroed, deactivated, tick off) and restored exactly as found the moment flight stops driving (bEnabled=false, the component deactivated, or the pawn torn down). Without this, UE runs both integrators against one body and the last ticker overwrites the pawn's velocity readout - and a CharacterMovement keeps applying gravity against the flight dynamics. Opt out per-instance with Pause Conflicting Movement Components, or globally with r.LcmNav.Flight.MovementAuthority 0. Two notes: stock MoveTo path-following still binds the pawn's original movement component, so drive an enabled flight component with FlyTo (or RequestVelocity) - and the pawn's root primitive must not have Simulate Physics enabled (the component warns in the log if it does).

Stopping at the goal (Hold Station When Idle)

A movement component is told what velocity to have, so "stop" used to mean "aim for zero velocity". A body with momentum then coasts until drag slows it down, and nothing brings it back. In our tests, bodies that arrived inside a 150 cm sphere and were told to stop ended up well past the goal: a multirotor 267 cm, a jet 936 cm, a fish 2369 cm, and the bird 14,790 cm away and still descending.

Hold Station When Idle (on by default, r.LcmNav.Flight.HoldStation) makes an unguided component steer back to the point guidance handed it over at, on a gentle brake-shaped approach with a deadband so a parked body is fully at rest. Any RequestVelocity call takes over immediately, so it only ever governs an otherwise-idle body. With it on, all four archetypes now settle within ~2 m of the goal and stay there.

Debugging the flight path - planned vs predicted vs flown

Turn on the navigation manager's bDrawPathfindingDebug (the master switch for all path debug) and a flight-component pawn draws three distinct lines:

line what it shows switch
Orange polyline + red spheres the PLANNED path the planner delivered manager bDrawPathfindingDebug
Magenta arc ahead of the pawn the PREDICTED dynamic flight path - the component's real dynamics rolled forward along the remaining route (look-ahead, banking, braking included) component bDrawDebugPrediction (default on) / r.LcmNav.Flight.DebugPredict, horizon r.LcmNav.Flight.DebugPredictSec
Green→red fading trail behind the FLOWN trajectory (speed-coloured), plus yellow = velocity and cyan = guidance arrows component bDrawDebugTrail (default off) / r.LcmNav.Flight.DebugTrail, lifetime r.LcmNav.Flight.DebugTrailSec

How to read them: the gap between orange and magenta is the body's physics (corner-cutting, brake distance - expected and correct); the gap between magenta and the trail is live avoidance (neighbours, walls - the prediction deliberately excludes what depends on other agents' futures). A lone agent whose trail leaves the magenta line is a tracking defect worth reporting. All three draw nothing in Shipping builds.

Winged bodies (Jet, Bird) - how they fly, and how to tune them

Both share one wing model, and it behaves like an aircraft rather than a hovering body:

  • Turns are made by banking. The heading error commands a bank; the banked lift supplies the centripetal force; the nose then follows the velocity. So a winged body has a genuine minimum turn radius, v² / (g·tan(MaxBankAngleDeg)) - 212 cm at 600 cm/s and 60°. Raise MaxBankAngleDeg (and MaxLiftFactor with it) for tighter turns; lower it for a heavy bomber.
  • Lift carries the weight, thrust only fights drag. At cruise the throttle sits near drag/MaxThrust (~0.12 at defaults). LiftCoeff sets how much airspeed the wing needs: weight is balanced when LiftCoeff·v² = Mass·980.
  • They cannot pinpoint-stop on aerodynamics alone. Commanded to a hard stop, a wing has nothing to push against. The Jet answers this with a thrust-vectored blend below WingBorneSpeed; the Bird flares to shed speed and hover-flaps to hold. Both rely on the nav layer's arrival ramp - with a constant full-speed command any fast forward-flyer orbits its goal, which is expected.
  • Arriving is not the same as staying. When a FlyTo task arrives it stops feeding guidance, and an unguided flight component holds the position it was left at rather than coasting to wherever momentum runs out (see Hold Station When Idle below). Without that a winged body sails past its goal and never comes back.
  • The Jet is Generic6DOF remodelled (the enum name is unchanged so existing content keeps working). r.LcmNav.Flight.JetGeneric 0 restores the previous hover-thruster behaviour exactly.

Notes:

  • A fast forward-flyer (bird/fish) can't pinpoint-stop; the nav layer's arrival slowdown makes it flare to a perch. Without arrival-aware guidance a fast body orbits its goal (expected).

  • Realistic dynamics lag guidance by design; raise MaxAcceleration for snappier, lower for heavier/driftier.

  • The two control loops are a cascade - tune them as a pair, never one alone. VelocityP is the outer loop (time constant 1/VelocityP); it commands a tilt that the inner AttitudeP/AttitudeD loop must then achieve. Keep the inner loop ~4× faster than the outer one, or the body wanders side to side and hunts back and forth around its goal:

    formula shipped default
    inner natural frequency wn = sqrt(AttitudeP) 7.75 rad/s
    inner damping ratio z = (AttitudeD + AngularDrag) / (2*wn) 0.84
    inner time constant 1/(z*wn) 0.15 s
    outer time constant 1/VelocityP 0.67 s

    Note: AngularDrag adds to AttitudeD - the integrator applies -AttitudeD*w and then -AngularDrag*w, so the loop's real damping is the sum. Raising AttitudeP for a snappier body without raising AttitudeD with it drops z below ~0.7 and the body visibly rings after every heading change. Damping must scale as 2*z*sqrt(AttitudeP).

Altitude while manoeuvring - MaxTiltAngleDeg and the thrust budget

A tilt-to-translate body (Generic6DOF / Multirotor) keeps only cos(tilt) of its thrust opposing gravity, so holding height while tilted needs a thrust-to-weight ratio of 1/cos(tilt):

tilt lateral accel available thrust-to-weight needed just to hold height
30° 566 cm/s² 1.15×
45° 980 cm/s² 1.41×
60° (default) 1697 cm/s² 2.0×
75° 3657 cm/s² 3.9×

MaxTiltAngleDeg caps this so the body cannot ask for a manoeuvre that costs it altitude, and when the thrust budget saturates the vertical axis is served first and the lateral axis takes the remainder. Note: raising the tilt limit without raising MaxThrust to match makes the body descend under hard lateral commands - the harder you ask it to move, the faster it sinks. Keep MaxThrust ≳ Mass * 980 / cos(MaxTiltAngleDeg); at the shipped 1 kg / 3000 / 60° there is 2× margin.

Reaching the commanded speed - drag is fed forward

The velocity loop cancels the drag it is about to apply, in the same way it cancels gravity. This is important, because drag is a constant disturbance for a proportional-only loop, and such a loop leaves a permanent offset of |drag| / (Mass * VelocityP). Without the cancellation, at the default settings that offset is 336 cm/s against a 600 cm/s command, so the body would cruise at 44 % of the speed it was given. No gain setting fixes that (raising VelocityP makes the error smaller, but the body then leans less visibly). Kill switch r.LcmNav.Flight.DragFeedForward 0.

Making a body lean (tilt-to-translate look)

A thrust-vector body leans because thrust must point along Mass*accel + weight. There is no cosmetic lean parameter in FlightDynamics mode - the attitude is physical, so you get lean by changing what the body has to do. Three separate mechanisms, commonly confused:

Want Knob Why
Forward lean while cruising LinearDragCoeff.X/Y ⬆ At steady speed accel≈0, so lean is exactly atan(drag/weight). No control gain can change this. 0.5→1.4 takes it from 10°→28° at 600 cm/s.
Lean while accelerating/braking VelocityP ⬇ Peak lean is atan(VelocityP*MaxSpeed/g) but it decays over 1/VelocityP, and the area is fixed. High gain = a spike too brief to see; low gain = a shallower lean actually held.
Bank into turns YawP ⬇ (keep ≪ AttitudeP) The body banks only while its velocity error is lateral. Fast yaw whips the nose onto the new heading first, making the error forward instead - pivot-then-go, no bank.

Note: In Kinematic mode none of the above applies: attitude there is cosmetic, driven by BankingAmount and MaxBankingAngle.

BankingAmount is now a multiple of the physically correct bank

BankingAmount (Kinematic mode, and the matching field on BT/StateTree FlyTo) is a multiplier on the coordinated-turn angle tan(bank) = V * yawRate / g. 1 is the true bank a real body holds in that turn; above 1 exaggerates it for readability; 0 flies wings-level.

Note: the default changed from 4 to 1, and an old value doesn't mean the same thing any more. The previous formula used a normalised per-frame velocity change, which loses how hard the turn is. As a result the roll command stayed near ±1 from ordinary velocity noise, and the body flicked between ±4° every frame in straight flight. With the new formula, a value of 4 reaches MaxBankingAngle in any normal turn. If you had authored a value here, re-tune it around 1. Legacy law: r.LcmNav.Flight.CoordinatedBank 0.

Flying straight up or down

Travel-referenced attitude is built by parallel transport of the previous frame, not from a world-up reference. This was needed because the two usual UE functions for building a rotation jump when the body travels straight up or down, and both were used before:

  • FVector::Rotation yaws by atan2(Y, X), which at X = Y = 0 is atan2(0,0) = 0: a body climbing straight up snaps its heading to world +X, then swings with any lateral noise.
  • FRotationMatrix::MakeFromXZ substitutes (1,0,0) for its up reference once |Fwd.Z| passes 1 - KINDA_SMALL_NUMBER - the frame teleports rather than degrading.

Either one makes a climbing or diving agent roll hard for reasons invisible in its flight path. World-up levelling is still applied, weighted by how horizontal the travel is, so it fades out exactly where the reference stops being meaningful and the body simply holds its roll through vertical. Applies to Kinematic, Bird, Fish and both FlyTo tasks. Kill switch r.LcmNav.Flight.ContinuousFrame 0.

The vertical axis has its own gain - VelocityPZ

VelocityP is held low on purpose: horizontally it commands a tilt the attitude loop then has to achieve, so it must stay ~4× slower than that loop. The vertical axis has no such constraint - thrust acts on it directly, with no attitude change in between - so making it share the slow gain costs bandwidth for nothing. Every production multirotor controller splits these (PX4 MPC_Z_VEL_P vs MPC_XY_VEL_P; ArduPilot PSC_VELZ_P vs PSC_VELXY_P).

Measured on a closed-loop rig flying a dead-level path, so any altitude motion is controller-generated:

VelocityPZ settled altitude wander settled vertical speed
legacy (shares VelocityP = 1.5) 40.3 cm 33.4 cm/s
2 26.1 30.3
4 (default) 6.0 cm 12.1 cm/s
8 5.4 9.9

Cross-track error and arrival time were unchanged in testing (173.8→173.6 cm, 10.85→10.83 s), so it has no cost horizontally. The value 4 comes from the maths: position-loop damping ζ = 0.5·√(Kz·L/v) reaches 1.0 at Kz=4 when the look-ahead equals the speed, and the velocity loop's damping against the rotor spool, ζ = 1/(2√(Kz·τ_spool)), is 0.707 at exactly Kz=4 with RotorSpinUpRate 8. Raise RotorSpinUpRate too if you push it much past 4.

A path that ends short of the goal no longer orbits

If the last waypoint of the path is more than 2 × Acceptance Radius from the goal, the task used to reset its index to that waypoint every tick. The agent was already within the acceptance radius of it, so on the next tick the waypoint was marked as reached and the index was reset again. In one test this happened 1750 times in 40 s, and the task never succeeded or failed. Now it does this once, holds position, replans twice, and then reports Failed with a log line that names the likely cause. Common causes of a short path: the goal quantises to a leaf centre, or r.LcmNav.SeamSafe.TruncateUnprovable (default ON) truncated the route at its first unprovable leg.

Troubleshooting - symptom to cause

Each row below is a cause in the design with its own console switch, so you can turn each one on or off separately. Go down the list in order. Don't start by re-tuning gains, because none of these problems comes from the gains.

Note: r.LcmNav.WallAvoidV2 is off (0) by default on purpose. An earlier attempt to weaken this push made one agent fail to arrive (it orbited, with 33 loop events), because a planned route sometimes points into a wall and only a full-strength push gets the agent clear. V2 keeps the full push at contact and only reduces it further away, but it hasn't been re-tested in that case yet. Turn it on if flyers judder near geometry, and check that they still arrive.

Agent scale - flying a body in a centimetre world

ULcmFlightMovementComponent::AgentScale (default 0) makes a body authored for a metre-scale world fly in a centimetre-scale one without retuning anything. The integrator runs in agent units: every FlightConfig value and every internal constant (gravity, the airspeed thresholds, the station-hold deadband) keeps its production meaning, and positions and velocities are converted at the component's boundary - world = agent x scale. 0 adopts the scale of the FlyTo task that drives the body (its own Agent Scale, or the navigation manager's World Scale); a positive value is explicit. At 0.01 a 1 m drone tuned for 600 cm/s flies as a 1 cm one at 6 cm/s, through the same path shape, in the same time - a similarity transform, not a retune. Two things follow from that: FLcmFlightState is reported in agent units (Speed01 is unchanged, Airspeed and VerticalSpeed read 600 at full speed whatever the scale), and the pawn's own collision and mesh must be scaled by the user - the plugin scales motion, not geometry. In a 120 x 70 x 40 cm aquarium at a 1 cm leaf, a drone at actor scale 0.01 flies the cave route it flies at 100:1.

Animation contract - FLcmFlightState

Every tick the component produces FLcmFlightState (archetype-agnostic where possible):

Field Meaning

VerticalSpeed cm/s, climb + / dive − - climb/dive pose blend

Consume it two ways:

  • Pull: GetFlightState (BlueprintPure) on the component, e.g. from an AnimBP's Update.
  • Push: implement ILcmFlightAnimInterface::ReceiveFlightState on your AnimBP (or pawn). The component calls it every tick (bBroadcastAnimState, default on). Cache the struct and drive:
    • GaitPhase → rotor/wing/tail cyclic pose (Sine/curve on the phase)
    • Speed01 + VerticalSpeed → locomotion blendspace
    • BankAngleDeg / PitchDeg → additive lean/pitch
    • GaitAmplitude01 → flap-vs-glide (bird) or effort (fish/drone) blend weight
    • RotorRPM → prop-spin material/WPO param (Multirotor)

Mass crowds & scale

The LCM Nav3D Agent trait (NavMode = PathFollowing) carries the same flight options (LocomotionModel, FlightArchetype, FlightConfig) - set them and a whole crowd flies with the identical 6-DOF physics as a pawn, still pathing, avoiding and arriving. With the default Kinematic, crowds behave exactly as before.

Dynamics LOD (the scale knob). Full 6-DOF per agent is expensive; set FlightDynamicsLODDistance (cm) so only agents within that distance of the viewer run full dynamics - everyone else uses the cheap kinematic integrator (face-velocity, no roll). So a 10K crowd keeps only the on-screen agents on the expensive path. 0 = always full. Global kill switch: r.LcmNav.Mass.FlightLOD (1 default / 0 = full everywhere). LOD switching is seamless - a far agent's integrator state re-syncs from its live transform when it returns to range.

Deferred (documented) scale extensions:

  • GPU 6-DOF compute for very large crowds is not included. The dynamics LOD on the CPU already limits the cost to the agents you can see, which is cheaper.
  • Shared flight config: FlightConfig is currently stored per entity. Sharing one copy per archetype would use less memory in large crowds, but that isn't done yet.

Determinism

The dynamics are deterministic: fixed integration sub-steps, no RNG or wall-clock; gust/jitter are seeded per-agent sinusoidal noise. Same input sequence → identical trajectory.

Bird and Fish do not share the drone control cascade

Note: StepBird and StepFish are separate integrators - they never call RunStep6DOF. That is on purpose (a bird doesn't move sideways by tilting a rotor), but it meant they also didn't have its velocity-tracking loop. Thrust only pushes along the body's forward axis, so in older versions nothing corrected a velocity error at right angles to the nose. The bodies pointed in the guidance direction and waited for drag, so errors across the path and in altitude only faded slowly and never reached zero. That was the cause of birds and fish "drifting away from the path points".

They now generate the perpendicular force a banked wing or a flexing body actually produces, bounded by what the body can physically supply - lift for the bird, tail/fin thrust scaled by swim effort for the fish. BankTurnGain is the rate (1/s) that converts a cm/s error into that demand, which is what its own description always claimed. Measured on one corner path, same guidance:

archetype cross-track before → after altitude error before → after
Generic6DOF (reference) 174.3 → 174.3 9.4 → 9.4
Multirotor (reference) 173.6 → 173.6 22.8 → 22.8
Bird 234.4 → 183.9 69.7 → 61.5
Fish 203.7 → 198.4 64.0 → 17.4

The two drone archetypes are not affected, because the change only touches the two integrators that didn't have the loop. Kill switch r.LcmNav.Flight.BodyManeuver 0.

Note: the bird's LiftControl trim is not a second vertical controller, so don't remove it. It is the only way the bird balances lift against gravity. Lift is LiftCoeff × airspeed², which at cruise is more than the body's weight, so without the trim the bird keeps climbing (in testing, altitude error went from 61.5 to 186.4 cm). The trim sets how strong the lift is, and the manoeuvre force pushes sideways. Both are needed.

Fish: the tail beats with the swim

A real fish's tail beats faster the faster it swims, with a swing of about a fifth of its body, and barely stirs at rest while the fins hold it. Tail Beat From Speed (Flight Config, Flight|Fish, on by default) drives the vertex-animated fish material that way; off, the older fixed beat plays.

Field Default Meaning
Tail Beat From Speed on The beat follows the speed in body lengths a second
Tail Beat Hz Per Body Length 1.33 Beats a second per (1 + body lengths a second): about 2.7 at 1 body length a second. Lower for a stiff swimmer (a tuna), higher for an eel-like one
Tail Beat At Rest Hz 0.7 The beat at rest
Tail Amplitude BL 0.2 The tail tip's swing while swimming, peak to peak, in body lengths. 0 = the material's authored swing
Tail Amplitude At Rest BL 0.05 The swing at rest

A fish with a skeletal mesh that plays one looping swim clip gets the same rate: Drive Swim Clip Rate on the Flight Movement component (LCM Flight|Anim, on by default) sets the clip's play rate from the beat. Swim Clip Beats Per Loop is how many beats one loop holds; 0 counts them from the clip's bones the first time it plays. An Animation Blueprint reads the same rate from the flight state (Gait Frequency Hz).

Schooling fish also keep out of each other's wake: Wake Avoid Weight (0.8) eases a fish off the axis of a schoolmate ahead within Wake Length BL (2 body lengths), so a school swims side by side and diagonally behind rather than nose to tail.

Fish schooling on pawns

The Flight Movement component has a Schooling group (LCM Flight|Schooling). Turn on Enabled and, whichever node drives the body - Fly To, Patrol, Follow, Orbit or Follow Flow Field - it steers as a school member instead of by the node's avoidance (reactive push, wall whiskers, flock separation): personal space, collision anticipation, heading matching and closing up with other agents (pawns and a Mass school alike), and turning away from rocks and glass before reaching them. The node's route still says where to go, and the fish's nose follows its travel (a Patrol's facing request is not made for it). Nodes that must be exact - Land, Take Off, Move To And Face, Use Smart Object, the evasions - keep their own steering.

On Patrol a schooling fish counts a waypoint as reached once the school has carried it past (beyond the waypoint along the leg into it, within 3 x the Arrival Radius), so a fish on the school's flank never turns back for a point it passed abeam.

The settings are the same as on a Mass crowd; the table and the leadership, predator, speed and burst-and-coast options are in the Mass Traits Reference. Three differ for pawns:

  • Informed Fraction does not apply: every pawn steers for its own route.
  • Contact Push (default 0.5) pushes apart overlapping bodies, scaled by overlap depth.
  • A predator is any body half again the fish's size or more that is not schooling with it, so a larger pawn on its own flight model (the Fish Tank's predator) sets off the escape.

A school on a loop (Feature Examples 2.7). Thirty fish on one Patrol loop, measured: give the loop dense waypoints (about a body length or two apart along the curve, the turns at least a metre in radius) and an Arrival Radius of about two spacings - each fish then makes for a point just ahead along the curve and its neighbours aim nearly alike. On twelve coarse points, fish at the same turn chased points 90-180 degrees apart and the school broke up at every end. Speed Coupling 0.4 keeps the school's shape along the straights; Threat Time Seconds 1.5 with Threat Range BL 2.5-3 lets it part round a predator without touching it.

With Enabled off, a Fish-archetype body still keeps its personal space - repulsion, collision anticipation and contact push, no heading matching, closing up, wall term, leadership or escape (r.LcmNav.FishSchool.PersonalSpace 0 turns that off). Every flight body is a neighbour to the others whether or not its pawn carries a Navigation Invoker.

Three more Fish-archetype rules, each with a kill switch:

  • Turn-aware arrival (r.LcmNav.Flight.TurnAwareArrival): the fish slows until its turning circle (speed / Max Turn Rate) fits the way onto the point it is making for, so it cannot circle a goal it came at from the side.
  • Stay in the water (r.LcmNav.Flight.FishStayInWater): a fish inside a Water Volume never leaves it; a step that would ends just under the surface, its velocity out through it dropped. A step into another Water Volume that carries on from it is water all the way: the fish swims on.
  • The water is a boundary (r.LcmNav.WaterSurfaceIsBoundary, r.LcmNav.WaterVolumeIsClosed): every face of a Water Volume - its surface, its sides and its floor - is blocked in the octree, so a swimmer's routes stay in the water and a flyer's stay out of it, glass or no glass. A face, or the part of one, that another Water Volume carries on from stays open. (Until 3.5 only the surface was: a route to a goal above the water left an open tank through its side, and the fish was held against that invisible wall for the rest of the run.) Volumes wider than r.LcmNav.WaterSurfaceMaxSizeCm (200 m - a sea) get no boundary.
  • A target out of the water (r.LcmNav.Flight.FishGoalInWater): a fish in a Water Volume chasing a target actor (a Fly To's goal object, the Fly To Location node's Target Actor) or patrolling a waypoint that is out of its water makes for the point of its water nearest it, a radius and a quarter in from the faces - up under bait over the surface, to the glass nearest a target beyond it. A fixed Fly To destination out of the water is the caller's mistake to hear about: it still fails with No Path. In sight of its goal (same water, nothing solid between) the fish swims straight at it, so it reaches the surface and the glass that the octree's padding (sized for the level's largest flyer) keeps routes off, and arrives there. Its route requests start and end on free water inside its own volume, never on the far side of the water's padded wall.

Console multipliers for tuning without editing assets: r.LcmNav.FishSchool.ScaleRepulsion, ScaleAnticipation, ScaleAlign, ScaleAttract, ScaleWall, ScaleEscape, ScaleContactPush, ScaleBrake (all 1 = as authored), r.LcmNav.FishSchool.MaxCommandDeg (-1 = the config's) and r.LcmNav.FishSchool.Leadership (0 = every fish steers for the goal).

Path following on 6-DOF bodies

Everything in this section applies only to a pawn driven by an enabled ULcmFlightMovementComponent in FlightDynamics (6-DOF) mode. The defaults are LocomotionModel = Kinematic and bUseFlightMovementComponent = false, so a pawn with default settings doesn't use any of it. Kinematic pawns, and pawns with no flight component, follow paths the same way they always have.

On a 6-DOF body the path follower works differently in four ways:

  • Sharp corners. The agent's position on the path is found by projecting it onto the path, not only by checking whether it came within Acceptance Radius of each waypoint. So a small Acceptance Radius no longer makes agents stick at corners that are tighter than their turning circle. r.LcmNav.PathProjectWindow (default 3) limits how far ahead the search looks, so on a hairpin the agent doesn't jump to the return leg before it has rounded the corner.
  • Stall detection. A stall means no progress along the path, not no movement. This way an agent that flies in circles is noticed and recovered. Turn it off with r.LcmNav.ProgressStallDetect 0. The progress threshold is r.LcmNav.ProgressEpsilonCm (default 50).
  • The look-ahead target. The point the agent steers at is pulled back along the path until there is a clear line to it in the octree. In a vertical shaft with offset openings, for example, this stops the agent aiming through a floor. Where there is no navigation data yet, the target is left unchanged. Turn it off with r.LcmNav.PursuitVisibleTarget 0.
  • Speed for corners. The agent plans its speed over the next few waypoints (r.LcmNav.SpeedProfilePoints, default 8) and starts braking early enough for every corner it can see. In testing, corner error stayed about the same from 300 to 1200 cm/s, and average speed hardly changed.

Acceptance Radius does not control how closely the agent follows the path. It only decides when a waypoint counts as reached. How tightly an agent can take a corner depends on its physics: the minimum turn radius is v²/a_eff, so waypoints closer together than that are always taken wide, however you tune it.
