LCM Nav3D vs Recast: navigation for flying AI

Applies to LCM Nav3D 3.6.0 · Unreal Engine 5.2 to 5.8 · Updated 22 November 2026

In short: Unreal's Recast navmesh tells an agent "where can I stand?". LCM Nav3D tells it "where is there empty air?". They do different jobs. If your project has both soldiers and aircraft, you will usually run both, and Tutorial 09 shows how.

Read this page if you are not sure which one you need. If you already know you need 3D navigation, go straight to Installation.

How they differ

Recast builds a surface. It is a mesh of convex polygons laid over the ground, and every point on it is a place where an agent could stand.

LCM Nav3D builds a volume. It is a sparse voxel octree that divides up the empty space in the level, so a valid position is anywhere an agent fits, even 200 metres up with nothing below it.

You cannot get the second from the first by changing settings. A navmesh only stores surfaces, so it has no way to say that a block of sky is free to fly through. Core Concepts explains how the octree stores that space, and why open sky takes up so little memory.

Common workarounds and their limits

Most teams try one of these before they look at 3D navigation. Some of them are the right choice for some projects, so each one is described below with where it stops working.

A navmesh plane at flight altitude

You put an invisible floor at 3000 units and let Recast build on it. This is cheap and it works as long as every agent flies at that one height. As soon as an agent has to dive under a bridge or climb over a building, it can't. Paths are still 2D, and there is no way to avoid things above or below.

Several stacked navmeshes

This adds more layers, and more work. You have to author the transitions between layers by hand. An agent also can't fly diagonally through the space between two layers, and for a flying agent that is most of the space.

A uniform 3D grid

A voxel grid does store volume, and A* on it works. The problem is memory. It grows with the cube of the level size, and empty sky costs as much as solid rock, so a 2 km level needs far too much. An octree fixes this: one large node can cover a big empty area, and it only subdivides near geometry.

Raycast steering with no pathfinding

You fire a few traces and steer away from whatever they hit. It is cheap and looks fine in open terrain. It breaks on concave shapes like a U-shaped canyon, a hangar with one door or a courtyard. Steering has no plan for the whole route, so the agent flies into the pocket and gets stuck there. Problems like this often only show up late in a project.

Hand-authored spline highways

Splines are predictable, cheap and easy to art-direct. For scripted flypasts and fixed patrol routes they are the right tool, and you don't need pathfinding for those. Agents on splines can't go to a goal you didn't plan for, though, and every new route has to be made by hand.

When Recast is the right answer

Recast is mature, free, well tested and already works with Behavior Trees, EQS and the crowd system. Use it when:

  • Your agents walk. That covers most games, and LCM Nav3D adds nothing for walking characters.
  • Your agents only look like they fly, for example a drone that hovers 50 cm above the floor and follows the terrain. Recast with a Z offset is simpler and cheaper.
  • Flight routes are fixed and scripted. Use splines.
  • You need Detour crowd avoidance for a ground army. That is Recast's UCrowdManager, and it works well.

When you need 3D navigation

  • Agents fly through open space and have to find their way through gaps, such as canyons, caves, asteroid fields or the air between city buildings.
  • Multi-level interiors where above and below both matter, and an agent should be able to choose between them.
  • Underwater or zero-gravity movement, where there is no floor to project onto.
  • You need tactical queries (cover, line of sight, height advantage) about points in the air as well as on the floor.
  • Agents must reroute around things that move, in three dimensions.

Running both in one level

Most projects with flying agents also have walking ones, and the plugin is built for that. Walking agents use Recast and flying agents use the octree, in the same level at the same time.

Add a ULcmCrowdAvoidanceBridge to a flying pawn and it registers with Unreal's stock UCrowdManager. Detour RVO then steers the Recast crowd agents around it. A Z-band filter stops agents at very different heights from avoiding each other for no reason. Tutorial 09 walks through the setup.

Recast keeps its navmesh and LCM Nav3D keeps its octree. The bridge is the only part that connects them.

Common questions

Can Unreal's navmesh handle flying AI at all?

Only roughly. A navmesh describes a walkable surface, so flying built on it is surface navigation with a height offset, or several stacked surfaces joined by hand. That works for a hover drone that follows the terrain. It doesn't work for an agent that has to pick its own height.

Do I have to choose between Recast and LCM Nav3D?

No. You can use both in the same level. Ground agents use Recast, flying agents use the octree, and a bridge lets Detour crowd avoidance see the flying ones.

Why an octree instead of a simple 3D grid?

Memory. A uniform grid uses as much memory for empty sky as for solid geometry, and the total grows with the cube of the level size. In an octree, one node can cover a large empty area, and it only subdivides near geometry. So the size of the navigation data depends mostly on how much geometry the level has.

Does this replace Unreal's navigation system?

No, it works alongside it. Recast, Behavior Trees, StateTree, EQS, AI Perception, Mass and the Gameplay Debugger all work as before. LCM Nav3D adds its own tasks, tests, traits and a debugger category to those systems.

Which engine versions are supported?

Unreal Engine 5.2 to 5.8, on Windows, macOS, Linux, Android, iOS, PlayStation 5 and Xbox Series X|S. See Installation for the full requirements.
